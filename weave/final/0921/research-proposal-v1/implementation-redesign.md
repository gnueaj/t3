# Weave 구현 재구성안 — 기록을 찾는 것에서, 지금 쓸 기억을 고르는 것으로

2026-09-23 · 검토용 v1 · 기존 기획서와 HTML·PDF·PPTX는 변경하지 않음

## 1. 무엇을 바꾸고, 무엇을 유지할까?

**전체 기획을 다시 짤 필요는 없습니다. Page 8의 구현 논리를 중심으로 고치고, Page 10의 삼성·시장 맥락을 그 논리에 맞추는 것이 좋겠습니다.**

기존 `Trigger → Routing → Search → Delivery`는 실행 순서를 설명하기에는 적합합니다. 다만 다른 검색형 AI에도 적용할 수 있어, Weave가 어디에서 어려운 판단을 하고 어떤 사용 경험을 만드는지 잘 드러나지 않습니다.

이번 안은 그 안에 숨어 있던 세 판단을 앞으로 꺼냅니다. **단서를 이어 찾기, 달라진 내용 확인하기, 건넬 순간 고르기.** 그중 ‘변경·완료·취소를 확인하는 기억 상태 관리’는 기존 안보다 명확하게 추가한 설계입니다. 단계 이름만 바꾸거나, 새 알고리즘을 발명했다고 주장하는 안이 아닙니다.

## 2. 전체를 묶는 질문

> **무엇을 찾아야 할지 정확히 말하지 못하는 순간에도, 흩어진 기록에서 지금 쓸 수 있는 기억을 건넬 수 있을까?**

이 질문에는 서로 다른 세 문제가 있습니다. 관련 기록을 찾는 것, 그 기록의 내용이 지금도 맞는지 판단하는 것, 지금 꺼내는 편이 도움이 되는지 판단하는 것입니다. 검색 유사도가 높다는 이유만으로 세 문제가 모두 해결되지는 않습니다.

### RQ1. 이름도 저장 위치도 몰라도, 단서를 이어 필요한 내용을 찾을 수 있을까?

**설계:** 요청에서 필요한 정보와 이미 아는 단서를 나눕니다. 먼저 찾은 기록의 인물·행사·날짜를 다음 검색의 조건으로 사용하고, 각 연결에 원문 근거를 남깁니다. 의미 검색과 키워드 검색은 후보를 찾는 도구이며, 어느 기록을 다음에 읽을지는 별도로 결정합니다.

**시나리오:** ‘지은이네 집들이 때 마신 와인’ → 집들이 일정에서 날짜 확인 → 해당 시간대 사진 후보 탐색 → 라벨 확인 → 출처와 함께 검색어에 반영. 같은 시기의 사진이라는 이유만으로 특정 와인을 마셨다고 확정하지 않고, 여러 후보가 남으면 사진을 고르게 합니다.

**검증할 가설:** 한 번에 관련 기록을 모으는 검색보다, 발견한 단서로 다시 검색하는 방식이 여러 기록을 이어야 하는 질문에서 정답과 필요한 근거를 더 잘 찾는가? 단순히 모델 호출을 많이 해서 생긴 효과인지도 확인합니다.

### RQ2. 찾은 기억은 지금도 맞는가?

**설계:** 원문을 보관하면서 그 안의 사실·일정·약속과 후속 변경 기록을 연결합니다. 같은 대상에 대한 변경·완료·취소 근거가 확인되면 현재 상태에 반영합니다. 최근에 나온 문장이라는 이유만으로 무조건 기존 내용을 덮어쓰지는 않습니다.

**시나리오:** 집합 시간이 8:40에서 9:10으로 변경됐다면, ‘오늘 집합 시간’에는 수정된 시간을 보여줍니다. 케이크를 이미 사다 줬다는 후속 대화가 확인된다면 같은 구매 기억을 다시 먼저 알리지 않습니다. 반면 사용자가 ‘그때 무슨 약속을 했지?’라고 직접 검색하면 완료된 약속도 이력으로 보여줍니다.

**검증할 가설:** 같은 기억의 후속 기록을 확인하는 방식이, 관련도나 단순 최신순으로 고르는 방식보다 오래된 답과 완료·취소된 일의 재알림을 줄이는가? 제대로 된 기억까지 불필요하게 숨기는 오류도 함께 봅니다.

**중요한 경계:** 완료 기록이 없다는 사실은 미완료의 증거가 아닙니다. 특히 대화 내보내기 이후의 발신 메시지 등 관측하지 못한 기록이 있으면 상태를 `확인 불가`로 남깁니다. ‘아직 안 사다 줬다’고 만들어내지 않습니다.

### RQ3. 요청하지 않은 기억은 언제 건네야 도움이 될까?

**설계:** 대화·위치 등 허용된 맥락이 바뀌면 관련 기억 후보를 찾고, 현재 관련성·유효성·행동 가능성·반복 노출을 함께 확인합니다. 직접 요청한 경우에는 후보와 확인 질문을 보여줄 수 있지만, 먼저 알릴 때는 더 엄격한 조건을 둡니다.

**시나리오:** 엄마와 대화 중이고 해당 부탁을 챙길 수 있는 상황이면 기억을 건넵니다. 같은 장소라도 이미 완료된 부탁이거나 지금 대화와 무관하면 표시하지 않습니다. 상태를 확인하기 어려우면 버튼을 먼저 강조하지 않고, 사용자가 요청했을 때 원문과 함께 확인하게 합니다.

**검증할 가설:** 관련성만으로 알리는 방식보다, 유효성·현재 상황·반복 노출을 함께 판단하는 방식이 불필요한 알림을 줄이면서 필요한 기회를 놓치지 않는가? 아무것도 알리지 않는 정책이 좋은 결과처럼 보이지 않도록 두 값을 함께 측정합니다.

세 RQ는 세 UX와 일대일 대응하지 않습니다. 세 UX가 같은 검색·상태 확인 기능을 공유하고, **얼마나 적극적으로 결과를 보여줄지**가 달라집니다. 일정 답장이나 과거 추천 장소처럼 다른 내용에도 같은 설계를 적용할 수 있습니다.

## 4. 파이프라인은 실제로 어떻게 바뀌나?

```text
사전 정리
허용된 기록 → 원문·출처·관측 범위 보관 → 검색 색인 + 사실·이벤트 후보
                                             ↕ 변경·완료·취소 근거 연결

사용 중
직접 검색 / 🧵 선택 / 허용된 맥락 변화
      ↓
필요한 정보와 이미 아는 단서 구분
      ↓
관련 기록 검색 ── 정보가 부족하면 발견한 단서로 다음 기록 검색
      ↓
같은 대상의 변화·충돌·관측 누락 확인
      ↓
직접 요청인가? ── 예 → 근거 있는 답 / 후보 선택 / 확인 요청
      │
      아니오
      ↓
지금 관련 있고, 근거가 충분하며, 행동 가능한가?
      ├─ 예 → 반복 노출 확인 → 🧵 표시 → 선택 후 확인·입력
      └─ 아니오·확인 불가 → 표시하지 않음
```

이 구조에서 기존 Trigger와 Delivery는 그대로 필요합니다. Routing과 Search를 없애는 것도 아닙니다. 그 사이에 **근거를 이어 찾는 검색 계획, 기억의 현재 상태 확인, 요청 방식별 전달 정책**을 명시적으로 둡니다.

### 4-1. 기록을 묶는 최소 단위

앱별 문서 목록 위에 ‘이 기록이 어떤 사실·사건·약속에 관한 것인가’를 얇게 덧붙입니다. 원문을 거대한 요약 하나로 대체하지 않습니다. 모든 메모를 할 일로 바꾸지도 않습니다.

| 저장할 정보 | 필요한 이유 |
| --- | --- |
| 원문 ID·출처·허용 범위·가져온 시점 | 근거 확인, 접근 제한, 삭제 반영 |
| 인물 ID·대상·행사 ID와 연결 근거 | 같은 이름의 다른 사람·다른 집들이를 섞지 않기 |
| 기록된 시각과 실제 사건·효력 시각 | 늦게 가져온 옛 기록을 최신 사실로 오해하지 않기 |
| 사실·이벤트의 종류와 후속 관계 | 일정 변경, 약속 완료, 취소 등을 원문에 연결하기 |
| 관측 범위·누락 가능성·확인 필요 여부 | 기록을 못 봤다는 이유로 사실을 단정하지 않기 |

초기 구현은 로컬 테이블과 관계 ID만으로 구성할 수 있습니다. ‘지식 그래프’라는 이름이나 전용 그래프 DB가 필수는 아닙니다. 자유 문장에서 추출한 관계는 처음에는 후보이고, 근거·인물·대상 일치 확인을 거쳐 사용합니다.

### 4-2. 역할 분담

| 구성 | 입력 → 출력 | 맡기지 않는 일 |
| --- | --- | --- |
| 의도·단서 추출 | 입력·허용된 맥락 → 필요한 정보, 인물·행사·날짜 후보 | 사용자의 속마음을 단정하지 않음 |
| 검색·다음 검색 선택 | 단서 + 검색 결과 → 다음 조회 조건, 근거 묶음 | 없는 날짜·이름을 채워 검색 경로를 만들어내지 않음 |
| 변화 확인 | 같은 대상의 원문·후속 기록 → 현재 사실 또는 상태·확인 필요 | 최근 문장을 무조건 정답으로 삼지 않음 |
| 전달 판단 | 근거 묶음 + 현재 상황 + 노출 이력 → 보여주기·확인 요청·보류 | 모델의 확신 표현만으로 먼저 알리지 않음 |
| 문장 구성 | 확인된 내용과 근거 ID → 답장·검색어·출처 카드 | 전달 성공을 실제 구매·약속 이행 완료로 기록하지 않음 |

임베딩·키워드 검색·Reranking은 기존 구현 후보를 유지합니다. sLLM은 제한된 형식으로 단서와 관계를 추출하거나 문장을 구성합니다. 검색 예산, 출처 접근, 상태 변경, 반복 노출 제한은 앱 로직이 관리합니다. LLM에 모든 판단을 한 번에 맡기는 형태를 피합니다.

검색 횟수·후보 수·알림 임계값은 단말에서 측정해 정합니다. 먼저 정한 숫자를 성능 근거처럼 제시하지 않습니다. 직접 요청에서는 후보가 애매할 때 사용자 선택으로 탐색을 좁힐 수 있습니다.

### 4-3. 상태를 확인하는 예

약속에 적용할 상태 예시는 `검토 중 / 진행 의사 확인 / 완료 근거 확인 / 취소 근거 확인 / 확인 불가`입니다. ‘진행 의사 확인’은 그 시점의 발화를 뜻하며, 현재까지 미완료라는 보장은 아닙니다. 현재 활용 가능성은 후속 기록의 관측 범위와 함께 따로 판단합니다.

```json
{
  "memory_id": "commitment-042",
  "kind": "commitment",
  "actor_id": "self",
  "beneficiary_id": "contact-mom",
```

원문 삭제·동의 철회 시 그 원문에서 만든 연결·상태·검색 결과 캐시도 갱신하거나 삭제합니다. 완료 사실만 따로 영구 보관해서 지워진 기록을 계속 활용하지 않습니다. ‘입력하기’를 눌렀거나 메시지를 작성했다는 이유로 약속을 완료 처리하지 않습니다.

## 5. 시나리오는 ‘같은 요청, 다른 기록’으로 증명합니다

기존 세 데모는 잘 동작하는 기본 장면으로 그대로 활용합니다. 그 뒤에 조건 하나만 바꾼 짧은 대비를 넣으면, 모델 이름을 설명하지 않아도 설계 차이가 보입니다. 아래 표의 기본 흐름은 기존 데모를 전제로 하며, 조건 변화에 대한 결과는 추가로 확인할 범위입니다.

| 장면 | 기본 흐름 | 한 가지 바꾼 조건 | 달라져야 하는 결과 |
| --- | --- | --- | --- |
| 업무 기록 | 메모·메일·나와의 채팅을 모아 오늘 준비 사항 확인 | ‘집합 8:40’ 뒤에 ‘9:10으로 변경’ 기록 추가 | 수정된 시간과 변경 근거를 안내. 옛 기록은 이력으로 남김 |
| 와인 이름 | 일정의 날짜로 사진을 찾아 라벨 확인 | 동명의 집들이 또는 다른 날 와인 사진 추가 | 엉뚱한 사진을 확정하지 않고 구분 단서 또는 선택 요청 |
| 케이크 기억 | 허용된 맥락에서 유효한 기억을 확인해 🧵 표시 | 같은 케이크를 전달했다는 명시적 후속 대화 추가 | 선제 표시하지 않음. 과거 약속을 직접 찾으면 이력 제공 |
| 케이크 기억 | 동일한 기록과 현재 상황 | 이후 대화 관측이 끊겨 이행 여부를 확인할 수 없음 | 미완료를 단정하지 않고 선제 표시 보류 |

데모에서 먼저 하나만 더 보여준다면 **케이크 완료 기록을 추가했을 때 버튼이 더 이상 뜨지 않는 장면**이 좋겠습니다. 이미 만든 데모 전체를 다시 만들지 않고, 같은 기억에 완료 근거가 추가됐을 때 전달 판단이 달라지는지만 확인합니다. 원문을 읽어 판단하는 범위와 시연용으로 구성한 부분이 있다면 발표자 참고에 구분합니다.

단어 하나에 반응하는 규칙처럼 보이지 않도록, ‘다른 케이크를 받았다’거나 ‘다음에는 사다줄게’ 같은 헷갈리는 후속 대화에서도 올바르게 구분하는지 확인합니다.

## 6. 무엇이 좋아졌는지 검증하는 방법

비교 대상은 특정 경쟁 서비스의 내부 구현이 아니라 **우리가 통제할 수 있는 기본 설계**로 둡니다. 같은 기록·질문·모델 조건에서 구성 요소를 하나씩 바꿉니다.

| 질문 | 기본 설계와 비교할 것 | 측정할 것 |
| --- | --- | --- |
| RQ1: 단서 연결 | 한 번 검색한 근거로 답하기 ↔ 발견한 단서로 후속 검색 | 필요한 근거를 모두 찾은 비율, 답 정확도, 잘못 연결한 비율, 호출 수·지연 |
| RQ2: 변화 확인 | 관련도/최신순 선택 ↔ 대상과 효력 시각을 확인한 상태 갱신 | 옛 정보로 답한 비율, 완료·취소된 기억의 재알림, 잘못 완료 처리한 비율, 확인 불가 처리 |
| RQ3: 전달 시점 | 관련성이 높으면 알림 ↔ 유효성·상황·반복 노출까지 확인 | 불필요한 알림 / 평가 기회, 필요한 기회를 포착한 비율, 반복 알림, 사용자 체감 도움·방해 |

RQ3는 **같은 기회 포착률에서 불필요한 알림을 얼마나 줄였는지**, 또는 같은 방해 수준에서 필요한 기억을 얼마나 더 건넸는지 비교합니다. 알림을 전부 꺼서 얻은 낮은 오알림률을 성과로 보고하지 않습니다. 관련성만 보는 기본 설계와 강화된 설계 양쪽의 임계값을 공정하게 조정합니다.

성공 사례뿐 아니라 변경·완료·취소·충돌·동명이인·관측 누락·도움 불필요 사례를 포함합니다. 같은 사람·행사·대화의 변형은 학습/조정용과 평가용에 나눠 섞지 않습니다. 날짜·인물·물건을 바꾼 처음 보는 사례에서도 확인합니다.

실제 사용 평가는 기존 방식과 Weave로 같은 종류의 일을 수행하게 하되, 순서 효과를 줄이도록 서로 다른 유사 과제를 번갈아 배치합니다. 완료 시간·앱 전환 수뿐 아니라 정답 여부와 방해감도 기록합니다. 소규모 결과는 참여 인원과 과제 범위를 함께 밝히고 전체 소비자 성과로 일반화하지 않습니다.

## 8. 기존 기술 부록에 붙일 설명과 실행 범위

기존 임베딩·Reranking·sLLM 정의는 유지합니다. 그 앞에 ‘RQ → 설계 → 대비 사례 → 검증 지표’를 두어 왜 해당 기술이 필요한지 먼저 설명합니다.

**기존 데모와 추가 검증:** UX 1·2·3의 기본 동작은 구현된 것으로 두고, 가상 또는 동의받은 기록의 변화·충돌·완료 조건을 추가해 결과가 달라지는지 확인합니다. 사용 경험의 구현과 실제 단말의 지연·전력·처리 위치 검증은 구분합니다. 외부 모델 호출이 있다면 온디바이스 구현이라고 표현하지 않으며, 제작 도구 이름만으로 처리 위치를 판단하지 않습니다.

**단말 검증:** 실제 허용된 입력 경로와 로컬 저장소를 사용해 검색·상태 관리·문장 생성을 측정합니다. 공개 API의 실행 조건이 맞지 않는 경우 자체 모바일 런타임 또는 삼성 내부 연동 경로를 별도로 검토합니다. 검증 전에는 모든 앱의 대화 맥락을 읽거나 상시 백그라운드 추론이 가능하다고 가정하지 않습니다.

**모델 추가 학습:** 처음부터 모두 학습할 필요는 없습니다. 규칙과 제한된 형식의 모델 출력으로 시작해, 평가에서 드러난 오류에 맞춰 의도 분류·관계 추출·검색 순위 조정 중 필요한 부분을 보정합니다. 예를 들어 ‘같은 케이크를 받았다 / 다른 케이크를 받았다 / 아직 못 받았다 / 기록이 없다’를 구분하는 근거 묶음을 만들어 변화 판단을 평가합니다. 개인별 원문은 검색 대상이며 별도 동의 없이 학습용으로 수집하지 않습니다.

모든 기록을 매번 다시 읽지 않습니다. 기록 갱신 시 해당 사실·사건과 연결된 부분만 업데이트하고, 사용 중에는 관련 후보만 확인합니다. 상태 관리와 전력 제한은 새로운 모델 이름을 늘리기보다, 저장 구조·조회 범위·실행 조건을 나누는 것으로 먼저 구현합니다.

## 9. 참고 근거와 주장 범위

아래는 이 안의 문제 설정과 구현 방향을 뒷받침하는 자료입니다. Weave의 신규성·성능·경쟁 우위를 증명하는 자료는 아닙니다. 신규성 조사를 완료했다거나 특허 가능성을 확인했다는 의미도 아닙니다.

- [IRCoT — ACL 2023](https://aclanthology.org/2023.acl-long.557/): 앞서 얻은 정보가 다음 검색을 바꾸는 다단계 검색 접근. Weave는 자유로운 추론문 자체보다 출처 ID와 구조화된 단서를 연결하는 제한된 조회 계획으로 검토합니다.
- [LongMemEval — ICLR 2025](https://arxiv.org/abs/2410.10813): 장기 기억을 정보 추출뿐 아니라 여러 대화의 연결, 시간, 정보 갱신, 답변 보류로 나누어 평가합니다. 이 안에서도 검색 성공과 변화 판단을 별도로 검증합니다.
- [Principles of Mixed-Initiative User Interfaces — CHI 1999](https://www.microsoft.com/en-us/research/publication/principles-mixed-initiative-user-interfaces/): 자동 도움과 사용자 제어를 함께 설계하는 관점. Weave의 선제 표시를 무조건 많은 알림이 아닌 도움과 방해의 균형으로 평가하는 참고입니다.
- [Samsung 개인화·보안 기반](https://news.samsung.com/global/samsung-introduces-future-ready-mobile-security-for-personalized-ai-experiences), [Google 온디바이스 API와 실행 조건](https://developers.google.com/ml-kit/genai): 실행 기반의 존재와 실제 연동 제약을 구분하기 위한 공식 자료입니다. 2026-09-23 확인.

**이 안의 핵심은 ‘새 모델을 만들었다’가 아니라, ‘단서를 이어 찾고, 바뀐 기억을 확인하고, 지금 건넬지를 구분해서 설계·검증한다’입니다.** 발표에서 이 차이가 드러나려면 이름보다 대비 장면이 먼저 보여야 합니다.
